# Feature Specification: Рефакторинг формы создания проблем

**Feature Branch**: `11-problem-registration-refactor`  
**Created**: 2026-01-30  
**Status**: Draft  
**Input**: Рефакторинг формы создания проблем с добавлением ручного ввода тегов и упрощенного UI

## Overview

### Цель
Упростить процесс создания проблем пользователями, адаптировав существующий функционал "аргументов" (Arguments/Contention) под концепцию "проблем" в социальной сети "Инкубатор идей".

### Контекст
В текущей версии Arguman пользователи создают "аргументы" через форму с избыточными полями ("Original Discourse", "Sources"), которые не нужны для концепции "проблем". Теги (nouns) привязываются автоматически через NLP-анализ текста, но отсутствует возможность ручного ввода тегов на уровне UI.

### Границы (Scope)
- **Включено**: Рефакторинг формы создания, добавление ручного ввода тегов, сохранение тегов, отображение тегов на странице проблемы
- **Исключено**: ИИ генерация тегов (#12), ИИ уточнение проблемы (#13), поиск похожих (#14), модерация (#15)

## User Scenarios & Testing

### User Story 1 - Создание проблемы с тегами (Priority: P1)

Пользователь хочет создать новую проблему и указать теги для её категоризации, чтобы другие пользователи могли легко найти проблемы по интересующим темам.

**Why this priority**: Это основной сценарий использования - без возможности создавать проблемы с тегами вся фича бессмысленна. Составляет MVP.

**Independent Test**: Можно протестировать, создав проблему с тегами и проверив, что проблема сохранена и теги отображаются на странице просмотра.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь на странице создания проблемы, **When** пользователь вводит текст проблемы "Как уменьшить пробки в городе?" и теги "транспорт, экология, город", **Then** проблема сохраняется в БД с привязанными тегами и пользователь перенаправляется на страницу просмотра проблемы
2. **Given** авторизованный пользователь создал проблему с тегами, **When** пользователь просматривает страницу проблемы, **Then** теги отображаются под заголовком проблемы как кликабельные элементы
3. **Given** авторизованный пользователь на странице создания проблемы, **When** пользователь начинает вводить тег "тран", **Then** система предлагает автодополнение из существующих тегов ("транспорт", "трансформация")

---

### User Story 2 - Создание проблемы без тегов (Priority: P2)

Пользователь хочет создать проблему без указания тегов, если он не уверен в правильной категоризации.

**Why this priority**: Важный сценарий для снижения порога входа - пользователь не должен быть обязан указывать теги.

**Independent Test**: Можно протестировать, создав проблему без тегов и проверив успешное сохранение.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь на странице создания проблемы, **When** пользователь вводит только текст проблемы без тегов и нажимает "Найти решение", **Then** проблема сохраняется успешно, система автоматически извлекает теги из текста (существующее поведение)
2. **Given** авторизованный пользователь создал проблему без ручных тегов, **When** пользователь просматривает проблему, **Then** отображаются только автоматически извлеченные теги (если есть)

---

### User Story 3 - Упрощенная форма создания (Priority: P1)

Пользователь видит упрощенную форму создания проблемы без лишних полей, что снижает когнитивную нагрузку.

**Why this priority**: Критично для UX - текущая форма содержит непонятные поля которые отпугивают пользователей.

**Independent Test**: Визуальный тест формы - должно быть только 2 поля (текст проблемы, теги) вместо текущих 3 (title, owner, sources).

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** пользователь открывает страницу создания проблемы, **Then** форма содержит только поля "Проблема" (textarea) и "Теги" (опциональное)
2. **Given** авторизованный пользователь на странице создания, **When** пользователь просматривает форму, **Then** кнопка отправки называется "Найти решение" вместо "Save and continue to edit"
3. **Given** авторизованный пользователь на странице создания, **When** пользователь вводит текст менее 10 символов, **Then** отображается ошибка валидации "Минимальная длина текста проблемы - 10 символов"

---

### User Story 4 - Фильтрация по тегам (Priority: P3)

Пользователь хочет найти все проблемы по определенному тегу, кликнув на тег.

**Why this priority**: Дополнительная функциональность для навигации, не блокирует основной функционал.

**Independent Test**: Можно протестировать кликом по тегу и проверкой списка проблем с этим тегом.

**Acceptance Scenarios**:

1. **Given** пользователь на странице проблемы с тегом "экология", **When** пользователь кликает на тег "экология", **Then** открывается страница со списком всех проблем с тегом "экология"

---

### Edge Cases

- Что происходит при вводе несуществующего тега? **Ответ**: Тег создается автоматически
- Что происходит при вводе слишком длинного тега (>30 символов)? **Ответ**: Ошибка валидации
- Что происходит при вводе тега с недопустимыми символами? **Ответ**: Тег нормализуется (только буквы, цифры, пробелы, дефисы)
- Что происходит при вводе более 10 тегов? **Ответ**: Ошибка валидации "Максимум 10 тегов"
- Что происходит при вводе дублирующих тегов? **Ответ**: Дубликаты игнорируются
- Что происходит если неавторизованный пользователь пытается создать проблему? **Ответ**: Редирект на страницу входа (существующее поведение)

## Requirements

### Functional Requirements

- **FR-001**: Система ДОЛЖНА убрать поля "Original Discourse" и "Sources" из формы создания проблемы (сохранив их в модели для обратной совместимости)
- **FR-002**: Система ДОЛЖНА переименовать поле "Argument" в "Проблема" и сделать его многострочным (textarea)
- **FR-003**: Система ДОЛЖНА добавить опциональное поле "Теги" с возможностью ввода тегов через запятую
- **FR-004**: Система ДОЛЖНА заменить текст кнопки "Save and continue to edit" на "Найти решение"
- **FR-005**: Система ДОЛЖНА перенаправлять пользователя на страницу просмотра проблемы после создания (не на edit)
- **FR-006**: Система ДОЛЖНА отображать теги проблемы на странице просмотра как кликабельные элементы
- **FR-007**: Система ДОЛЖНА автоматически создавать новые теги при вводе несуществующих
- **FR-008**: Система ДОЛЖНА предоставлять автодополнение при вводе тегов (AJAX-запрос к существующим тегам)
- **FR-009**: Система ДОЛЖНА валидировать текст проблемы (минимум 10, максимум 5000 символов)
- **FR-010**: Система ДОЛЖНА валидировать теги (максимум 10 тегов, каждый 2-30 символов)
- **FR-011**: Система ДОЛЖНА нормализовать теги (lowercase, trim whitespace)
- **FR-012**: Система ДОЛЖНА сохранять обратную совместимость с существующими аргументами

### Key Entities

- **Contention (Проблема)**: Представляет проблему пользователя. Ключевые атрибуты: title (текст проблемы), user (автор), language, date_creation. Связь M2M с тегами уже существует через поле `nouns`.

- **Noun (Тег)**: Ключевое слово для категоризации проблем. Атрибуты: text, slug, language, is_active. Уже существует в системе.

- **Keyword**: Синонимы для тегов. Уже существует в системе.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Форма создания проблемы содержит максимум 2 поля (текст проблемы + теги) вместо текущих 3
- **SC-002**: 100% созданных проблем с тегами корректно отображают теги на странице просмотра
- **SC-003**: Клик по тегу ведет на страницу фильтрации проблем по этому тегу
- **SC-004**: Все существующие аргументы остаются доступными без ошибок (обратная совместимость)
- **SC-005**: Валидация не позволяет создать проблему с текстом < 10 символов или > 5000 символов
- **SC-006**: Валидация не позволяет указать более 10 тегов
- **SC-007**: Автодополнение тегов работает с задержкой < 300ms

## Dependencies

### Внутренние зависимости
- **Блокирует**: Фичи #12 (ИИ теги), #13 (ИИ уточнение), #14 (поиск похожих), #15 (модерация)
- **Зависит от**: Нет (базовая фича)

### Внешние зависимости
- Django 5.2+ (уже установлен)
- jQuery (уже есть в проекте для autocomplete)
- Существующие модели `Contention`, `Noun`, `Keyword`

## Assumptions

1. Существующая модель `Noun` подходит для роли "Тега" без значительных изменений
2. Связь M2M между `Contention` и `Noun` (поле `nouns`) может использоваться для ручных тегов
3. Пользователи знакомы с концепцией тегов
4. Модерация тегов не требуется в MVP (любой может создать новый тег)
5. Автодополнение достаточно реализовать через простой AJAX без NLP
